2026-08-17 (continued): timing-offset bug found and fixed
-----------

While debugging a data-quality question raised during na model group
analysis (also switching first_level_glm_na.sh from -polort 6 to -polort A
- see below), found that essentially every subject's block-onset timing was
silently misaligned relative to their actual fNIRS recording - not a
data-cut/truncation problem, a clock-reference-frame bug.

Root cause (01_dataConversion/fnirsoft2nii/export2nii.py):
  - marker2onsetdur() wrote block onset times using the RAW recording's
    absolute clock (e.g. block 5 onset = 510.705s for 1068KP).
  - data2nii() builds the exported .nii starting at marker -5 (task start),
    so frame 0 of the .nii is NOT absolute time zero - it's whatever the
    raw clock read when marker -5 fired (96.56s for 1068KP; ranges 12-232s
    across the dataset, median 35.6s).
  - Nothing subtracted that offset. 3dDeconvolve is called with
    -local_times, which (per AFNI docs) interprets onsets as relative to
    the start of the analyzed run (frame 0) - so every block in every
    subject's design matrix was scheduled up to ~4 minutes away from where
    it actually happened in the data.

This is what caused the apparent "block 4 truncation" above: comparing
absolute-clock onsets against the (offset, but otherwise essentially
complete) recording made block 4 look almost entirely missing for ~99% of
subjects, when correcting for the marker -5 offset showed the real
recordings were fine (413/439 had >=99% of block 4 actually captured once
correctly time-aligned).

Fix: marker2onsetdur() now subtracts marker -5's time from every onset
before writing onsetdur.txt, so times are run-relative as -local_times
expects. Also added a -skip_nii flag to export2nii.py (regenerate only
timing.txt/onsetdur.txt, skip the slow per-timepoint .nii reconstruction -
unaffected by this bug, so didn't need to be redone) and fixed a few
hardcoded /mnt/speyside paths (this dataset is also mounted at
/mnt/highlands and /mnt/bellevue; the paths are now resolved relative to
the script's own location).

Also found and fixed, while regenerating: marker2onsetdur() assumed
exactly one each of markers -5,101-105,106 with no validation. Two subjects
have malformed marker sets that passed the existing trim_marker()
try/except (which only catches missing start/end markers, not wrong
counts/duplicates in between) and crashed the batch:
  0020P - a duplicate 101 marker (dropped by drop_duplicates, keep='last')
  0028P - markers 104 and 105 entirely missing (task was cut short) -
          already flagged in this file, 2026-02-02 entry ("Missing
          Markers"); confirmed still has no prp_0028P.*.mem.fnirs.nii at
          all, i.e. was never converted for the corsi task, unrelated to
          this bug.
Added a check right after trim_marker() that verifies the full expected
marker set is present, skipping (not crashing) subjects that aren't.
0020P recovered via a second acquisition attempt in its raw files after
the first was correctly skipped; 0028P remains excluded (no data).
